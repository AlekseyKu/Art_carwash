# Фича 06: Клиентское PWA «Автомойка АРТ»

**Статус:** spec (документация; код не начат)  
**Связано:** cloud-api, local-api catalog/clients, касса `PosPage` / `ClientSidePanel`, отчёты `/reports`, бренд [06-brand.md](../06-brand.md), бэклог G2/G4/A5 ([03-backlog-ideas.md](03-backlog-ideas.md))

Клиенты в интернете **не ходят на кассу**. Касса и админка — local-first на мини-ПК. PWA работает через **cloud-api**; каталог и записи синхронизируются со станцией. Оплата в первой поставке с записью — **только на мойке**.

---

## Цель

Отдельное мобильное PWA для клиента мойки:

1. Онбординг: сплэш → описание → регистрация (телефон + пароль **и** согласие на ПДн на одном экране).
2. Прайс-лист из админки (цены по классу авто, как на кассе).
3. Запись на мойку (услуги + слот); календарь тех же слотов на кассе.
4. Личный кабинет: профиль, несколько авто (госномер, класс), история записей и моек.
5. Собственник видит ленту записей (не в клиентском меню).

Новое приложение `apps/pwa` (Vite + React + `vite-plugin-pwa`). **Не** смешивать с kiosk-UI кассы в `apps/web`. Шрифт Montserrat. Цвета PWA — **тёмно-красный + графит `#303236`** (рекомендуемый набор «Гранат» в [06-brand.md](../06-brand.md)); киоск пока остаётся на текущем фиолетовом, палитру перенесём позже.

## Архитектура

```
[PWA клиент] ──► [cloud-api]
                    ▲     │
     каталог, клиенты│     │ записи, профили
                    │     ▼
[Касса / Админ] ──► [local-api] ──► SQLite станции
```

Источник правды:

| Данные | Где правда | Sync |
|--------|------------|------|
| Каталог, часы, длительности услуг | Станция (админка) | local → cloud (снимок) |
| Аккаунт клиента, гараж, записи из PWA | Cloud | cloud → local (pull) |
| Оплата, чек, смена | Станция (касса) | order.paid → cloud (как сейчас, плюс client/plate) |

Конфликты: оплаченный локальный заказ = source of truth. Запись из PWA не проводит оплату.

## Онбординг при старте

Приложение **не пускает в меню**, пока клиент не создал аккаунт (или не вошёл).

Повторный запуск: сплэш → сразу три вкладки (сессия сохранена).  
Нет сессии: сплэш → вход (телефон + пароль), **без** повторных тезисов.

```
Запуск → 0. Сплэш
            ├─ сессия есть ──────────────► три вкладки
            └─ сессии нет
                  ├─ первый запуск ──► 1. Тезисы → 2. Регистрация + ПДн → вкладки
                  └─ онбординг уже был ► Вход / регистрация (+ ПДн, если новый аккаунт)
```

### 0. Сплэш (каждый запуск)

- Полноэкранно, логотип «Автомойка АРТ», фон **графит** `#303236`, акцент логотипа/подложки — тёмно-красный.
- Пока грузятся shell, Montserrat, проверка сессии; каталог — **после** входа.
- Минимум ~0.8–1.2 с, чтобы лого не мелькало; дальше — до готовности.
- Нет кнопок, нет скипа.

### 1. Тезисное описание (только первый запуск)

Один экран (не карусель), 3 тезиса:

- **Прайс** — актуальные цены по классу авто, как на мойке.
- **Запись** — выбрать услуги и время, приехать без очереди.
- **Кабинет** — свои авто, госномера и история визитов.

«Далее» → регистрация. Ссылка «У меня уже есть аккаунт» → вход (без тезисов).

### 2. Регистрация + согласие на ПДн (один экран)

Один скроллируемый экран. Аккаунт создаётся **одной** кнопкой «Зарегистрироваться» — отдельного шага «Подтвердить» нет.

**Поля**

- Телефон РФ (`+7`), маска, нормализация как в CRM (цифры, `+7…`).
- Пароль + повтор, минимум 8 символов. На сервере **bcrypt hash**, не plaintext.

**ПДн (152-ФЗ) — на этом же экране, под полями**

- Короткий текст: кто оператор, зачем данные (запись, связь, история моек), без согласия аккаунт не создаётся.
- Чекбокс «Я согласен(на) на обработку персональных данных» — **обязателен**; без него «Зарегистрироваться» неактивна.
- Ссылка на полную политику (страница / PDF в PWA). Версия: `privacy_policy_version`.
- В аккаунте: `pdn_accepted_at`, версия документа, телефон.

Кнопка «Зарегистрироваться» создаёт аккаунт и открывает приложение. Ссылка «У меня уже есть аккаунт» → экран **Входа** (телефон + пароль, без чекбокса ПДн).

«Забыли пароль» — не в первой поставке (фаза D, сброс по SMS). SMS OTP в v1 не нужен.

Юридический текст политики и оферты готовит заказчик. В продукте — слот под контент и техническая фиксация согласия.

## 1. PWA: три экрана (нижняя навигация)

После онбординга:

```
┌─────────────────────────────┐
│  контент вкладки            │
├──────────┬─────────┬────────┤
│  Прайс   │ Запись  │Кабинет │
└──────────┴─────────┴────────┘
```

### 1.1 Прайс-лист

- Данные из админки: `catalog_tabs`, услуги, товары, матрица `service_prices` по классу.
- Клиент выбирает класс авто (те же классы и иконки, что на кассе).
- Пустая цена в матрице → услуга **скрыта** (как на кассе).
- Товары — одна цена, без класса.
- Офлайн: service worker кэширует последний успешно загруженный прайс.
- Блок «О мойке» внизу экрана: адрес, часы, телефон, карта — **без** четвёртого пункта меню.

### 1.2 Календарь / запись

- Авто из гаража (или класс + госномер, если гараж пуст) → услуги → дата → свободный слот.
- Слоты: часы работы × `duration_minutes` услуг × **2 поста**. Слот занимает один пост.
- Статусы записи: `booked` → `arrived` → `in_service` → `completed` | `cancelled` | `no_show`.
- Оплата на мойке. Напоминание SMS/push за 1 час — желательно, не блокер фазы C.

### 1.3 Личный кабинет

- Аккаунт уже есть. Выход из сессии. Смена пароля — позже.
- Профиль: имя (можно дозаполнить после регистрации), телефон (логин, не менять в v1 без отдельного сценария).
- **Гараж:** несколько авто — госномер, класс, кличка («серый кроссовер»).
- История записей и прошедших моек (оплаченные заказы, матч по телефону / госномеру).
- Повтор прошлого набора услуг в один тап → экран записи.

## 2. Касса и админка на станции

Сейчас CRM на кассе выключена (`ClientSidePanel` не монтируется в `PosPage`), календаря нет.

### 2.1 Календарь дня на кассе

```
        Пост 1              Пост 2
09:00   [запись Иванова]    [свободно]
10:00   [моют / заказ #12]  [запись Петрова]
11:00   [свободно]          [свободно]
```

- Две колонки (пост 1 / 2), слоты на выбранный день.
- Отличие walk-in (заказ с кассы) и записи из PWA.
- Клиент приехал → «Прибыл» → услуги из записи в **черновик заказа** → обычная оплата.
- Предупреждение, если walk-in пересекается с бронью.
- После оплаты: `bookings.local_order_id` + статус `completed`.

### 2.2 Клиенты на кассе

- Поиск по госномеру / телефону: профиль, авто, ближайшая запись, история визитов.
- Несколько авто на клиента (после миграции с одного `plate_number`).
- Панель клиента можно вернуть вместе с этой фичей (не ждать ANPR): ручной поиск. ANPR ([01](01-entry-camera-anpr.md)) позже подставляется в тот же профиль.

### 2.3 Админка станции

Новые настройки:

- Часы работы (по дням недели) и исключения.
- `duration_minutes` у услуг (для расчёта слота).
- Блокировка слотов: перерыв, ремонт поста.

Каталог по-прежнему редактируется только на станции; в cloud уходит снимок.

| Поле | Тип | |
|------|-----|---|

#### Расписание

- `schedule_settings` — день недели, open/close, длительность слота-сетки (или слот = сумма `duration_minutes`).
- `blocked_slots` — post_id, starts_at, ends_at, reason.
- `services.duration_minutes` — на станции, в снимке каталога.

### Снимок каталога в cloud

Не дублировать CRUD каталога в cloud. Хранить последний snapshot (tabs, services с duration, vehicle_classes, service_prices, site name/hours/contacts), который отдаёт `GET /api/customer/catalog`.

### Миграция local `clients`

Сейчас: один `plate_number` на клиента.

1. Телефон = идентичность клиента (матч с `customer_accounts.phone`).
2. Госномера → `vehicles` (локальное зеркало).
3. Старый единственный номер → первое авто.
4. `orders.client_id` сохраняем; поиск на кассе — по телефону или любому госномеру гаража.

`loyalty_accounts` остаётся на `client_id` станции; UI лояльности не в этой фиче.

### Outbox / sync (новые типы)

| Тип | Направление | Когда |
|-----|-------------|-------|
| `catalog.snapshot` | local → cloud | сохранение каталога / цен / часов / duration в админке |
| `customer.upsert` | cloud → local | регистрация, правка профиля/гаража |
| `booking.upsert` | cloud → local | новая/изменённая запись |
| `booking.status` | local → cloud | прибыл / в работе / completed / no-show |
| `order.paid` | local → cloud | **расширить payload**: client phone, plates, customer_id если известен |

## API (эскиз)

Auth клиента: `Authorization: Bearer <customer token>`.  
Owner: существующий owner token. Касса: washer token на **local-api**.

### Cloud: клиент

| Метод | Путь | Описание |
|-------|------|----------|
| POST | `/api/customer/register` | `{ phone, password, pdnAccepted, privacyPolicyVersion }` → account + session. Без согласия — 400 |
| POST | `/api/customer/login` | `{ phone, password }` → session |
| POST | `/api/customer/logout` | инвалидация session |
| GET | `/api/customer/me` | профиль |
| PUT | `/api/customer/me` | имя и т.п. |
| GET | `/api/customer/catalog` | снимок каталога + классы + цены + «о мойке» |
| GET/POST/PUT/DELETE | `/api/customer/vehicles` | гараж |
| GET | `/api/customer/slots?date=&serviceIds=&vehicleId=` | свободные слоты |
| GET/POST | `/api/customer/bookings` | список / создать |
| POST | `/api/customer/bookings/:id/cancel` | отмена клиентом |
| GET | `/api/customer/history` | записи + оплаченные мойки |

### Cloud: собственник

| Метод | Путь | Описание |
|-------|------|----------|
| GET | `/api/owner/bookings?date=` | лента записей дня/недели |
| POST | `/api/owner/bookings/:id/cancel` | отмена со стороны мойки |

Существующий `POST /api/owner/login` и analytics без изменений.

### Local: касса / админ

| Метод | Путь | Описание |
|-------|------|----------|
| GET | `/api/bookings?date=` | календарь дня по постам |
| POST | `/api/bookings/:id/arrive` | прибыл → черновик заказа с позициями |
| PUT | `/api/admin/schedule` | часы, blocked slots |
| PUT | `/api/admin/services` | + поле `durationMinutes` |
| GET | `/api/clients?query=` | поиск телефон / госномер (несколько авто) |

Pull с cloud на станцию: периодический + при открытии календаря (не блокирует офлайн-оплату walk-in).

## Фазы реализации (код — после этой спецификации)

Код в этом файле не ведётся, пока статус `spec`. Ниже — порядок будущих PR.

### Фаза A — Прайс в облаке + оболочка PWA + онбординг

- Outbox `catalog.snapshot` → cloud.
- `GET /api/customer/catalog` (только с customer session).
- `apps/pwa`: манифест, SW, сплэш, тезисы, экран регистрации (телефон + пароль + чекбокс ПДн), три вкладки, рабочий прайс по классу, палитра «Гранат» + графит.

### Фаза B — Кабинет и CRM на кассе

- Сессии клиента, профиль, гараж.
- Sync клиентов вниз на станцию; миграция `clients` → телефон + `vehicles`.
- Касса: поиск клиента, несколько авто, история (бэклог A5 / часть G2).
- История моек в PWA: расширить `order.paid` payload (phone, plate).

### Фаза C — Запись

- Слоты, PWA-календарь, календарь на кассе, конвертация записи → черновик заказа.
- Собственник: лента записей на день/неделю (`/reports` ± PWA).
- Оплата на мойке.

### Фаза D — позже (не первая поставка с записью)

- Лояльность UI (этап roadmap «Лояльность»): баллы, уровни, персональная скидка.
- Предоплата / депозит против no-show (G6).
- SMS-подтверждение номера и сброс пароля.
- Telegram Login / Mini App — тот же `customer_accounts`.
- Push «машина готова», NPS после визита (G9).
- Абонементы / пакеты (G1).
- Онлайн-оплата всей суммы + 54-ФЗ.
